Class 9

Making a save trustworthy When several changes make up one decision, and several people can act, what makes a save trustworthy?

One button, two changes

A Meridian reviewer opens a pending support case, reads the evidence and chooses NEEDS_INFO.

They press Save. On the screen, that is one action.

Inside the database, it is two. The case itself must now show that it has been reviewed, along with

the decision. Separately, the review history must record who made that decision. One row describes

where the case stands now. The other records the event that put it there.

Now imagine only one of them happens.

HALF-SAVE 1 HALF-SAVE 2 The case says REVIEWED A review event exists

But no review event exists. Nobody can say who But the case still says PENDING. The next reviewer made the decision or when. may pick it up again.

Each row looks plausible on its own. Read together, they tell a story that doesn’t add up.

Would you be comfortable telling the user that this save is complete?

Think of a bank transfer. Taking money out of one account and putting it into another are one

transfer. Nobody calls it complete just because the money was taken out. In Class 9, updating the

case and recording the review belong together in the same way.

Seeing a change is not the same as accepting it

Up to now, every statement we ran was saved the moment it succeeded. That works when one

statement is the whole job. It stops working when the job needs two.

Class 9 · Pre-read 1

An Analogy

Think of packing a parcel before it is sent out. While you are packing, you can:

▸​ look inside and check what is there,

▸​ swap something out, or

▸​ abandon the parcel entirely.

Once the parcel has gone out, “cancel packing” does not bring it back. Fixing it now takes a

new, deliberate action.

A database gives us the same two stages. We can group changes, inspect them, and then either

accept the whole group or cancel the whole group. Your own screen may show a change that the

database has not accepted yet. Seeing it and accepting it are two different facts.

We will also try the uncomfortable path. The first change succeeds and the second one fails. Should

we keep the first change because it worked? Or should we cancel the whole attempt because the

action is incomplete?

Two reviewers, two old photocopies

Now add a second person. Reviewers A and B are both authorised, and both open the same pending

case.

10:00 10:01 10:03 Both open the case A saves NEEDS_INFO B saves from the old screen

Each screen correctly shows Complete and correct. The real B’s screen still says PENDING. B PENDING. record now says REVIEWED. chooses READY_FOR_HANDOFF.

B’s screen hasn’t updated itself. It is a faithful copy of 10:00, like a photocopy of the office register.

Both saves are complete, every ID is valid, and no statement fails. Even so, B quietly replaces A’s

accepted decision.

Every query succeeded. So what went wrong?

Meridian’s rule is that once a review is accepted, a decision made from an older screen must not

silently replace it. That rule did not come from SQL. The product team decided it. Our job is to make

the save enforce it.

Class 9 · Pre-read 2

A number that travels with the case

One way to catch the old photocopy is to number each copy. The case carries a version number,

which starts at 1 and goes up every time an accepted change is made. When A saves, the case moves

to version 2. B is still holding version 1.

The save then asks one extra question at the very moment it writes:

UPDATE lab_cases
SET    review_status = 'REVIEWED', ...
WHERE  case_id = 'C9-DEMO'

AND version = 1 AND review_status = 'PENDING';

In plain words: change this case only if it is still the version I opened, and it is still pending.

If nothing matches, nothing changes. That is not an error. It is a useful result: the case changed while

you were looking at it. The reviewer sees a clear message and looks again, rather than overwriting

someone else’s work.

Worth Noticing

A version number doesn’t judge which decision is better. It only answers one question: “Is the

stored case still the one I reviewed?” Fetching the newest number behind the scenes just to

push an old decision through would defeat the point.

Words you will hear

You don’t need to memorise these before class. Each one will be attached to something you have

already watched happen.

YOU WILL HEAR IN PLAIN WORDS

Transaction A group of changes treated as one unit: accepted together or cancelled together.

COMMIT Accept the changes in this group.

ROLLBACK Cancel the changes in this group that have not been accepted yet.

ACID Four names for the guarantees a transaction gives. Class 9 attaches each name to something you have already seen happen.

Version check Save only if the record is still the version you opened. Sometimes called optimistic concurrency.

Row lock Reserve the record briefly while saving, then check it again. Sometimes called the pessimistic approach.

What will Class 9 do?

Class 9 uses a deliberately small lab with two tables: one holds a case’s current state, the other holds

its accepted reviews. With so little schema, the behaviour is easy to see. You will:

✓​Define what one complete save means when it needs more than one change.

✓​Make a change, inspect it, cancel it, then make it again and accept it.

✓​See why a failed second step must cancel the whole attempt.

✓​Watch two reviewers overwrite each other, even though every query succeeds.

✓​Add a version check, then practise both outcomes: one row saved, zero rows saved.

✓​Compare that approach with briefly reserving the record while saving.

A small setup step, if you have MySQL Workbench: go to Edit → Preferences → SQL Editor

and turn on Stop Script Execution On Errors. This stops a script from carrying on, and saving

half an action, after one of its statements fails.

What to bring to class

Nothing to submit. Bring three questions in your head.

Completeness

If a save updates the case but fails to record who made the decision, has anything 1 been saved? What should the user be told?

Freshness

Your screen was correct when you opened it. Is it still safe to save from it ten 2 minutes later? How would you know?

Ownership

Who should decide whether a completed review can be changed later: the database, 3 or the business?

In Class 8, we improved what the Meridian database could represent. Class 9 asks what happens
